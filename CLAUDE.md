# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Docker image that wraps OCRmyPDF (with jbig2 and unpaper) for unattended batch OCR of scanned PDFs. There is no application source code — the entire project is a `Dockerfile`, a single shell entrypoint script, and a GitHub Actions pipeline that builds/tests/publishes the image. Changes to this repo are almost always edits to one of those, or to `README.md`.

## Architecture

- `Dockerfile` — single-stage build on `ubuntu:24.04`.
  - Installs Tesseract (with `deu`, `eng`, `fra`, `por`, `spa` language packs), Ghostscript, `unpaper`, `jbig2`, `qpdf`, `pngquant`, `inotify-tools`, and installs `ocrmypdf` itself (pinned via `ARG OCRMYPDF_VERSION`) into a Python venv at `/app`. Ghostscript stays installed even though `ocrmypdf` also ships `pypdfium2` as a pip dependency — Ghostscript is still needed as the fallback renderer for `--output-type pdfa`.
  - Creates a dedicated `ocrmypdf` user/group at UID/GID `1001` (`1000` was tried first but collides with the `ubuntu` account `ubuntu:24.04` already ships at that UID) and sets `USER 1001:1001` as the image default — **the container is non-root by default**, not just optionally.
  - `/in`, `/out`, `/processed` are created and `chown`ed to `1001:1001` at build time, then declared as volumes. A real deployment almost always bind-mounts over them, so their runtime ownership depends on the *host* directories, not this default.
  - `chmod -R a+rX /app` after the pip install ensures the non-root user can actually read/traverse the venv, since the `RUN` steps that create it still execute as root during the build (`USER` only affects the runtime `ENTRYPOINT`, not build steps) — verified empirically rather than assumed to be fine.
  - `root/entrypoint.sh` is copied to `/entrypoint.sh`, explicitly `chmod +x`'d (belt-and-suspenders beyond relying on the source file's mode bit surviving `COPY`), and set as the `ENTRYPOINT`.
  - `ARG OCRMYPDF_VERSION` is preceded by a `# renovate: datasource=pypi depName=ocrmypdf` comment so Renovate (see `renovate.json`) can bump it automatically — keep that pairing intact when changing it, and keep the value double-quoted (`="x.y.z"`) for the regex to match.
  - `IMAGE_VERSION`/`IMAGE_CREATED` build args and OCI labels are normally overridden by the pipeline's `compute-version` job (see below); the in-file defaults only matter for a manual `docker build .` with no `--build-arg`s.
  - There used to be a multi-stage `download` step that fetched a `su-exec` binary for privilege-dropping. It's gone — see below for why.

- `root/entrypoint.sh` — the entire runtime logic:
  1. If the container's command is `help` (e.g. `docker run ... help`), it `exec`s `ocrmypdf -h` and exits immediately — no permission checks, no folder access. This is also how the README tells users to look up `OCRMYPDF_OPTIONS` flags, since the flag list isn't duplicated in the README anymore.
  2. `check_permissions()` — derives the running identity from `$(id -u)`/`$(id -g)` (there's no separate `MAP_UID`/`MAP_GID` env var — see below for why that was removed) and, for each of `IN_FOLDER`/`OUT_FOLDER`/`PROCESSED_FOLDER`, checks both **ownership** (must be owned by that UID/GID) and **real access** (`[ -x/-r/-w folder ]` — a genuine `access()`-style check from the actual running process, not a hand-rolled reimplementation of Unix permission logic, so it correctly accounts for anything the raw ownership check wouldn't, e.g. owned correctly but missing a permission bit). Any failure `exit 1`s with a specific error; it never attempts to auto-fix anything.
  3. `process_file()` — given a filename, if it ends in `.pdf` (case-insensitive), runs `ocrmypdf ${OCRMYPDF_OPTIONS} "${IN_FOLDER}/<file>" "${OUT_FOLDER}/<file>"` **directly** (no privilege-dropping wrapper — the process already *is* whatever UID/GID it's going to run as). On success, moves the source file to `PROCESSED_FOLDER`. On failure, logs an error and leaves the file in `IN_FOLDER` for retry on next restart.
  4. On startup, processes every existing file in `IN_FOLDER`, then watches it via `inotifywait` (`create`/`moved_to`) for new files, calling `process_file` per event.
  5. Graceful shutdown: a `SIGTERM`/`SIGINT` trap sets a `terminate` flag. The watch loop uses `read -t 1` (not a plain blocking read — a blocking `read` on a pipe is *not* reliably interrupted by a trapped signal in bash, it just retries on EINTR) so it periodically rechecks the flag even when idle. Whatever file is currently mid-`process_file` is allowed to finish; no new file is started once the flag is set.

  **Why there's no more `su-exec`/root path, and no more `MAP_UID`/`MAP_GID`**: an earlier version of this image ran as root and used `su-exec` to drop to a configured UID/GID for the actual OCR/move calls. That's gone entirely — `su-exec` unconditionally calls `setgroups()`/`setuid()`/`setgid()` even to self-target the same UID it's already running as, which need real `CAP_SETUID`/`CAP_SETGID` in the process's *effective* capability set; a non-root Docker `user:` only gets those into the *bounding* set via `cap_add`, not the effective set (confirmed empirically: `su-exec: setgroups(1001): Operation not permitted`). Since nothing OCR-related needs any privilege at all, the fix was to remove privilege-dropping entirely rather than route around it: the image now defaults to non-root (`USER 1001:1001`), `process_file` never elevates or drops anything, and the whole container can run with `cap_drop: ALL` and zero `cap_add` — verified end-to-end. A `MAP_UID`/`MAP_GID` env var pair briefly existed after that change (an "expected identity" declaration, checked against `$(id -u)`/`$(id -g)` for a friendlier error message) but was removed as redundant: since the check required them to equal the real running identity anyway, they added a second place to configure the same thing without adding any real safety — the ownership/access checks alone still catch a misconfigured `--user`/`user:`, just via a slightly more generic message.

- Configuration is entirely environment-variable driven (see README for the full table): `IN_FOLDER`, `OUT_FOLDER`, `PROCESSED_FOLDER`, `OCRMYPDF_OPTIONS`. `OCRMYPDF_OPTIONS` is passed through unquoted/unescaped to `ocrmypdf`. The valid flag list isn't duplicated in the README — it's looked up live via `docker run --rm <image> help`. To run as a UID/GID other than the default `1001:1001`, change the container's actual user (`--user`/`user:`) and the ownership of the bind-mounted host folders together — `check_permissions()` will catch it clearly if they disagree.

## CI/CD (`.github/`)

- `workflows/pipeline.yaml` — the main pipeline (multi-arch build, integration tests, CVE scans, tagged releases, dual publish to GHCR + Docker Hub). Adapted from the sibling repo `../docker-languagetool`'s pipeline; job structure mirrors it closely.
  - `compute-version` derives the image tag from `Dockerfile`'s `ARG OCRMYPDF_VERSION` line as `${OCRMYPDF_VERSION}-N`, where `N` auto-increments per existing matching git tag. On a tag push, the tag itself is the version. The `on.push.tags` filter (`[0-9]+.[0-9]+.[0-9]+-[0-9]+`) uses GitHub's glob dialect, not regex — `+` here means "one or more of the preceding atom", not a literal plus.
  - `integration-test-image` runs the `.github/tests/*.yml` compose variants (see below) on both `ubuntu-latest` and `ubuntu-24.04-arm` runners.
  - Requires these secrets to actually succeed: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY` (a GitHub App used for tag creation, since tags pushed with the default `GITHUB_TOKEN` don't retrigger workflows).
- `workflows/reusable-super-linter.yaml` — generic reusable Super-Linter wrapper, called with `devops-only: true` (this repo has no application-language code to lint).
- `linters/` — Super-Linter sub-tool configs. `.hadolint.yaml` ignores `DL3008` (unpinned apt package versions — deliberate policy, not an oversight) and `DL3047` (wget without a progress bar).
- `tests/*.yml` — docker-compose variants for `integration-test-image`, not to be confused with the root `docker-compose.yml` (that one's the user-facing example referenced from `README.md`). All bind-mount `/in`, `/out`, `/processed` (required for this project, unlike optional volumes in other images), `cap_drop: [ALL]` with zero `cap_add` (nothing needs any capability anymore):
  - `default.yml` — image defaults only, no `user:` override (the documented zero-config path).
  - `custom-uid-ro.yml` — `user: "1002:1002"`, plus `read_only: true` + `tmpfs: [/tmp]`, proving both the UID-override mechanism and the hardened-rootfs profile together. `/tmp` stays `noexec` — Docker's default — since nothing executes anything from it; verified empirically rather than assumed.
  - Every variant's bind-mounted host folders must be pre-chowned to the UID/GID that variant expects before `docker compose up` (the entrypoint verifies ownership/access but never fixes it). Do this via a disposable container with an **explicit `--user 0:0`** override — `docker run --rm --user 0:0 -v ...:/in ... --entrypoint=chown <image> -R <uid>:<gid> /in /out /processed`. The `--user 0:0` is required now (it wasn't before): the image itself defaults to a non-root user, so without the override the `chown` process wouldn't have permission to change ownership to an arbitrary UID either.
  - The integration test drops `tests/fixtures/sample.pdf` (a synthetic, no-real-data image-only PDF) into `/in` and retries the copy (via `cp` to a temp name + `mv`, which re-triggers a `moved_to` event) if the output hasn't appeared yet — a single fire-and-forget write occasionally misses its `inotify` event on some Docker backends, so the retry isn't optional defensive fluff.
- `renovate.json` — the Dockerfile custom-manager regex matches *any* `# renovate: datasource=... depName=...` comment immediately followed by `ARG ..._VERSION="..."`; this is why `OCRMYPDF_VERSION` must stay quoted.

## Working in this repo

- Local build/run without CI:
  ```sh
  docker build -t ocrmypdf-batch .
  mkdir -p in out processed && sudo chown 1001:1001 in out processed
  docker run --rm -v $PWD/in:/in -v $PWD/out:/out -v $PWD/processed:/processed ocrmypdf-batch
  ```
  The `chown` step is required, not optional — the container is non-root by default now, and `check_permissions()` will refuse to start otherwise. Drop a scanned PDF into `./in` before/while the container is running to exercise the OCR path. `docker run --rm ocrmypdf-batch help` prints `ocrmypdf`'s own `--help` and exits without touching any volumes.
- To chown to some other UID/GID for testing (e.g. matching the `custom-uid-ro.yml` CI variant), use a disposable container with `--user 0:0` rather than host-level `sudo` when testing from CI or a sandbox without cached `sudo` credentials — see the `tests/*.yml` note above.
- `in/`, `out/`, and `processed/` at the repo root (and under `.github/tests/`) are local scratch/test volumes (gitignored) — not part of the shipped image content.
- To test multi-arch changes to the `Dockerfile` locally: `docker buildx build --platform linux/amd64,linux/arm64 -t ocrmypdf-batch:test .` (or one platform at a time). The Dockerfile used to have a multi-stage `su-exec` download step with an actual amd64-only arch-detection bug and a missing `ca-certificates` bug, both only caught by testing `linux/amd64` specifically — that step is gone now, but it's a reminder that single-arch-only local testing (e.g. just building on an arm64 Mac) can miss real bugs.
- To lint the `Dockerfile` the same way CI does: `docker run --rm -v "$PWD/Dockerfile:/Dockerfile:ro" -v "$PWD/.github/linters/.hadolint.yaml:/.hadolint.yaml:ro" hadolint/hadolint hadolint -c /.hadolint.yaml /Dockerfile`.
- To validate workflow YAML: `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest` catches more than plain YAML syntax checks (e.g. mismatched reusable-workflow inputs).
- When changing installed Tesseract language packs or other apt packages, update the "Installed Tesseract-OCR languages" line in `README.md` to match.
- When bumping the `ocrmypdf` pin, no README update is needed for flags anymore (it points at `docker run ... help` instead of a static list) — just update `ARG OCRMYPDF_VERSION` in the `Dockerfile`.
